## Ограничения и решения для следующего агента

- Docker недоступен в среде агента (gVisor); инициализация БД проверяется
  официальным `docker-entrypoint.sh` образа `postgres:16` на локальных
  бинарниках. Контейнеры и Windows не запускались.
- Реальные доступы Mail не запрашивать в открытом журнале; для A14 нужны
  безопасно переданные аккаунты и разрешённые получатели.
- Локальный PostgreSQL для разработки: `scripts/setup-preview-db.sh` (порт
  55432, роль `mailcontrol_app` без superuser). `scripts/dev-api.sh start|worker|stop`
  запускает собранный API и процессы отправки против демо-БД.
- Время в расчётах квот и повторов берётся из `server/clock.ts`; тесты
  переводят его через `setClock`, не дожидаясь суток.
- Временная ошибка на стадии получателя/письма (`scope: "message"`) не
  охлаждает аккаунт; ошибка соединения/входа/`MAIL FROM` — охлаждает до 15 мин.
- Требование сервиса «ждать дольше» распознаётся только по коду/тексту как
  временная ошибка; точную длительность из ответа Mail не извлекаем.
- `mailcontrol/.local/` и `.hoplite/` в Git не попадают.

### 2026-09-23 — M1: исправление запуска в Docker и перенос в отдельный репозиторий

**Статус:** исправление выполнено и проверено на Linux; запуск на Windows
пользователя после исправления ещё не подтверждён. M2 не начинался.

**Причина сбоя:** первый запуск `START-EMPTY.cmd` на Windows 10 (Docker Desktop)
завершился `dependency failed to start: container mailcontrol-db-1 is unhealthy`.
В логе БД: `permission denied to alter role — The bootstrap user must have the
SUPERUSER attribute`. Скрипт `docker/20-role.sql` пытался снять права
суперпользователя с bootstrap-роли `mailcontrol` (`POSTGRES_USER`), а PostgreSQL 16
это запрещает. Инициализация обрывалась, контейнер перезапускался уже без
init-скриптов, но `compose up --wait` к этому моменту уже зафиксировал отказ.
Ошибка воспроизведена локально официальным `docker-entrypoint.sh` образа
`postgres:16`: тот же текст ошибки, entrypoint завершается до старта сервера.

**Изменения:**

- `mailcontrol/compose.yaml`: bootstrap-роль теперь `mailcontrol_admin`;
  приложение по-прежнему подключается ролью `mailcontrol`. Healthcheck БД идёт
  по TCP (`pg_isready -h 127.0.0.1`), потому что временный сервер на этапе
  инициализации слушает только Unix-сокет — иначе `app` мог стартовать раньше
  готовности настоящей БД. Добавлен `start_period: 20s`.
- `mailcontrol/docker/20-app-role.sql` (вместо `20-role.sql`): создаёт роль
  `mailcontrol` LOGIN без superuser/createdb/createrole/replication с паролем из
  `POSTGRES_PASSWORD` через `\getenv` и передаёт ей владение БД `mailcontrol`.
  Файл выполняется один раз только на пустом томе.
- `mailcontrol/README.md`: пункт диагностики с точным текстом ошибки, объяснение,
  что том неудачного запуска пуст и совместим, и как удалить **только пустой** том,
  чтобы получить ограниченную роль. Уточнён статус проверки Docker.
- Версия 0.1.1 в `package.json`, `package-lock.json`, `server/app.ts`,
  `shared/contracts.ts`, `scripts/package.py` — чтобы отличать исправленный

### 2026-09-23 — M2–M5 одним этапом, версия 1.0.0

**Статус:** реализовано и проверено на Linux; частично — открытые пункты
приёмки перечислены ниже. Выполнено по прямой команде пользователя «выполняй
все этапы за раз» после второго сбоя запуска в Docker.

**Причина второго сбоя Docker:** `password authentication failed for user
"mailcontrol"` — том остался от первого запуска, а `.env` создан заново в новой
папке. Исправление: `docker/sync-app-role.sh` при каждом старте выставляет
пароль роли приложения из `.env` (работает и с томом старой версии, где
`mailcontrol` — bootstrap-суперпользователь, и с новым). Режимы стали
отдельными Compose-проектами (`mailcontrol-local`, `mailcontrol-demo`),
`launch.cmd` поднимает БД → синхронизирует пароль → собирает app и worker и при
сбое сам печатает логи.

**Изменения:** см. «Где продолжать». Ключевые решения внутри плана:

- Очередь: резерв (`FOR UPDATE SKIP LOCKED`, владелец, токен, срок) → переход к
  отправке в одной транзакции с блокировкой рассылки → задачи → аккаунта
  (`SKIP LOCKED`) и проверкой статуса, группы, отключения и квоты; порядок
  блокировок «рассылка → задача → попытка» одинаков для паузы, остановки,
  исключения, решений и фиксации исхода; конфликты 40P01/40001 повторяются.
- Квота: `quota_usage` со состояниями `reserved | accepted | possible |
released`; `quota_used`/`quota_next_free` — SQL-функции с параметром времени.
- Adapter-контракт `accepted | rejected(category, scope) | unknown`; SMTP-клиент
  собственный, стадия `message` (терминатор уже отправлен) даёт `unknown`.
- Тестовая отправка — отдельная рассылка `is_test` на один адрес через ту же
  очередь. Поздний ответ по решённой попытке пишется в `late_*` и ничего не меняет.
- Пароли: AES-256-GCM, ключ `mailcontrol.key` в томе `…-secrets`, `key_id` при
  шифротексте; импорт никогда не обновляет пароль существующего аккаунта.
- Интерфейс: модальные окна через портал в `document.body` со счётчиком
  открытых окон (стек «мастер + подтверждение» освобождал страницу неверно).
